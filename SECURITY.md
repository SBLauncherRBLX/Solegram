# Безопасность Solegram

Этот документ описывает, как Solegram защищает аккаунт пользователя от вредоносных плагинов, какие уязвимости нашёл аудит движка плагинов и как они закрыты. Здесь же лежат протоколы безопасности проекта: что делать при установке плагина, при обнаружении вредоносного плагина, при сообщении об уязвимости и при выпуске версии.

Код, о котором идёт речь, лежит в:

- `TMessagesProj/src/main/java/com/solegram/messenger/plugins/`: анализатор, список блокировки, контроллер, страж выполнения;
- `TMessagesProj_App/src/main/python/`: среда Python, страж `solegram_guard.py`, установщик пакетов `solegram_pip.py`.

---

## 1. Модель угроз

**Что защищаем, по важности:**

1. **Доступ к аккаунту:**
   - ключи сессии (`tgnet.dat`);
   - вход на другое устройство (QR-вход, экспорт авторизации);
   - облачный пароль, номер телефона, активные сеансы, удаление аккаунта.
2. **Деньги и ценности:** звёзды, подарки, право собственности на чаты.
3. **Переписка и контакты:** база сообщений, настройки, сохранённые данные.
4. **Целостность приложения:**
   - файлы плагинов;
   - сама среда Python;
   - установленные пакеты;
   - кэш сгенерированных классов.

**От кого:**

- **Обычный вредоносный плагин.** Это готовый «стилер»: читает `tgnet.dat` или настройки и отправляет их в Telegram-бот, Discord-вебхук или на файлообменник. Так выглядит большинство реальных случаев.
- **Замаскированный плагин.** Вредоносная часть скрыта от проверки: строки собираются на ходу, код раскодируется из base64 и запускается через `exec`, нужные классы Java достаются по имени.
- **Атака через цепочку поставки.** Плагин сам чистый, но тянет пакет PyPI с вредоносным кодом, нативной библиотекой или модулем, подменяющим системный.
- **Плагин, изменяющий другие плагины.** Он дописывает код в чужой, уже проверенный файл, чтобы тот выполнился без проверки.
- **Другое приложение на телефоне.** Оно пытается подключиться к серверу разработчика плагинов на `127.0.0.1`.

### Честная граница

Плагины Solegram — это код на Python в процессе приложения, с прямым доступом к Java через мост Chaquopy. Так их можно делать совместимыми с exteraGram. Настоящей «песочницы» внутри одного процесса не бывает. Плагин, специально написанный против самого Solegram, может через рефлексию Java дотянуться до любой внутренней структуры, в том числе до проверок ниже.

Поэтому защита многоуровневая, и каждый уровень закрывает свой класс атак:

- **Анализ и проверка пользователем** отсекают то, что видно в коде.
- **Страж выполнения** ловит то, что от анализа спрятали, и останавливает типовые вредоносные действия, даже если их не заметили.
- **Щит аккаунта** в Java защищает самое ценное там, где запросы обходят Python.
- **Список блокировки** выключает уже известные вредоносные плагины у всех пользователей.

Обход всех уровней сразу требует целенаправленной работы именно против Solegram. Анализатор отмечает такую работу как подозрительную: рефлексию, доступ к внутренностям плагинов, попытки найти стража.

## 2. Уровни защиты

### 2.1. Статический анализ (`PluginSecurity`)

Каждый файл плагина проверяется до установки и перед каждым запуском, без выполнения кода.

- Исходник разбирается как токены Python: слово в комментарии или строке не считается вызовом.
- Импорты и псевдонимы разрешаются.
- Вызовы сопоставляются с примерно 80 правилами в 8 категориях: сеть, сообщения, действия, секреты, файлы, код, система, интерфейс.
- Отдельно оцениваются сочетания, которые имеют смысл только для вредоносного кода:
  - секреты и сеть;
  - раскодирование и `exec`;
  - скрытые строки и сеть;
  - shell и сеть;
  - и другие.
- Отчёты кэшируются по SHA-256 файла. Когда правила меняются, увеличивается `PluginSecurity.VERSION`, и все отчёты считаются заново.

Правила против обхода самой защиты (`sec_tamper`, критично):

- `gc.get_objects`, `gc.get_referrers`, `gc.get_referents`, `sys._current_frames`;
- `java.chaquopy`, подмена `builtins.__import__`;
- упоминание `solegram_guard`, `__sg_plugin__`, `plugin_libs`, `plugin_dex`, `PluginRuntimeGuard`;
- упоминание настроек и файлов самой защиты.

### 2.2. Список блокировки (`plugins_blocklist.txt`)

Это публичный список SHA-256 известных вредоносных плагинов в репозитории дистрибутива.

- Solegram скачивает его по HTTPS не чаще раза в несколько часов.
- Плагин из списка не устанавливается и не запускается.
- Уже установленные плагины из списка выключаются, пользователь видит уведомление.
- Слишком большой ответ считается ошибкой, и остаётся прежний список. Обрезанный список молча разблокировал бы всё, что не вошло.

### 2.3. Согласие пользователя, привязанное к точному файлу

- Перед установкой и перед включением показывается отчёт анализа. Пользователь принимает решение о конкретном файле.
- Принятый SHA-256 запоминается.
- **Новое:** перед каждым запуском файл хешируется заново. Если хеш не совпадает с принятым, плагин не запускается и выключается, а в списке у него стоит «изменился после проверки». Включить его снова можно только после повторной проверки.

Так закрыт способ, когда один плагин дописывает код в другой, уже проверенный. Закрыта и любая другая подмена файла на диске.

- Плагины, которые были включены до появления этой проверки, при первом запуске новой версии принимаются один раз в текущем виде.
- Если пользователь отключил проверку перед установкой, принятым считается файл, который он сам установил или включил.

### 2.4. Блокировка опасных плагинов (по умолчанию включена)

Плагин с вердиктом «опасный» не устанавливается и не запускается.

- **Новое:** настройка теперь включена у всех по умолчанию. При обновлении её один раз включают и тем, у кого она была выключена.
- Выключить её можно в «Плагины → Безопасность».

### 2.5. Страж выполнения (`solegram_guard.py` + `PluginRuntimeGuard`)

**Новое.** Страж ставится до запуска среды плагинов, до первого плагина и до первого пакета. Он работает так:

- **Через аудиторский хук CPython (PEP 578).** После добавления его нельзя снять средствами Python.
- **Через обёртку `jclass`.** Это имя, через которое плагины получают классы Java.
- **Через обёртку `__import__`.** Так обрабатывается вид `from java.lang import Runtime`.
- **Через проверку в `hook_utils.find_class`.**

**Кому принадлежит действие.** Модуль каждого загруженного плагина регистрируется у стража по идентичности словаря его глобальных имён. Действие считается действием плагина, если в стеке есть кадр его кода. Это касается:

- функций самого плагина;
- потоков, которые он запустил;
- обратных вызовов, переданных в Java;
- библиотек, которые он вызвал.

Для запуска кода из строк (`exec`, `compile`, `marshal`) учитывается только непосредственный вызывающий. Поэтому `dataclasses`, `namedtuple` и импорты, которые сами пользуются `exec`, плагину не мешают.

**Разрешения берутся из отчёта.** Плагин может делать во время работы только то, что анализ нашёл в его коде и пользователь видел:

| Разрешение | Откуда берётся | Что без него останавливается |
|---|---|---|
| сеть | любая находка категории «Сеть» | `socket.connect`, `bind`, `sendto`, `getaddrinfo`, `gethostbyname`; классы `java.net.URL`, `Socket`, `HttpURLConnection`, `InetAddress`, `javax.net.*`, `okhttp3.*`, `WebView` |
| shell | `sys_shell` | `subprocess`, `os.system`, `os.exec*`, `os.spawn*`, `fork`, `pty`, `os.kill`; `java.lang.Runtime`, `ProcessBuilder`, `Process`, `android.system.Os` |
| нативный код | `code_native`, `sys_native_lib` | `ctypes` (dlopen, dlsym, вызовы, адреса); запись файлов `.so`, `.dex`, `.jar`, `.apk`, `.pth` в данные приложения |
| dex | `sys_dex` | `dalvik.system.*`, `ClassLoader` |
| код из строк | `code_exec`, `code_exec_static` | `exec`, `eval`, `compile` из кода плагина |
| десериализация | `code_deserialize` | `marshal.loads`, `pickle` |
| установка приложений | `sys_install` | `PackageInstaller` |

Если вызов спрятали от анализа (собрали имя из строк, раскодировали), разрешения у плагина нет, и вызов останавливается в момент выполнения.

**Запрещено всегда, независимо от отчёта:**

- **Чтение секретов:**
  - `tgnet.dat` (ключи сессии);
  - `cache4.db*` (база сообщений);
  - всё в `shared_prefs` (настройки, конфигурация аккаунтов);
  - всё в `databases`;
  - файлы самой защиты.
- **Запись в файлы, от которых зависит выполнение кода:**
  - код в папке плагинов (`.py`, `.plugin`, `.pyc`, `.pth`, `.so`, `.dex`, `.jar`);
  - пакеты (`plugin_libs`);
  - сам Python и SDK (`chaquopy`);
  - сгенерированные классы (`plugin_dex`, `code_cache`).
- **Обходные пути:**
  - символические и жёсткие ссылки на секреты;
  - переименование в защищённые места;
  - пути с `..`, через `/data/data/…` или через ссылки (пути приводятся к реальным).
- **Поиск стража:**
  - `gc.get_objects`, `gc.get_referrers`, `gc.get_referents`, `sys._current_frames`;
  - импорт `solegram_guard` из кода плагина.
- **Внутренние классы защиты и секретов приложения:**
  - `PluginRuntimeGuard`, `PluginGuard`;
  - `SolegramSecrets`, `ApiCredentials`.

Свои файлы данных плагин по-прежнему может писать куда угодно, в том числе в папку плагинов. Остановленное действие получает `PermissionError`. Его видно:

- в уведомлении «Solegram остановил плагин …»;
- на странице плагина, в разделе «Остановлено во время работы».

Потоки, которые остались от выгруженного плагина, продолжают считаться его кодом, но разрешений у них больше нет.

### 2.6. Щит аккаунта (`PluginRuntimeGuard` в `ConnectionsManager`)

**Новое.** Самые опасные запросы Telegram проверяются в Java, в самом начале `ConnectionsManager.sendRequest`, на потоке вызывающего. Это происходит до очереди, которая теряет информацию о том, кто отправил запрос.

Плагин не может отправить, ни через SDK, ни через Java напрямую:

- **Вход:** `auth.acceptLoginToken` (вход чужого устройства по QR), `auth.exportLoginToken`, `auth.importLoginToken`, `auth.exportAuthorization`, `auth.importAuthorization`, `auth.importBotAuthorization`;
- **Сеансы:** `auth.resetAuthorizations`, `auth.logOut`, `account.resetAuthorization`, `account.setAuthorizationTTL`, `account.changeAuthorizationSettings`, `account.resetWebAuthorization(s)`;
- **Пароль:** `auth.checkPassword`, `auth.recoverPassword`, `auth.requestPasswordRecovery`, `account.getPasswordSettings`, `account.updatePasswordSettings`, `account.getTmpPassword`, `account.resetPassword` и действия с почтой пароля;
- **Аккаунт:** `account.deleteAccount`, `account.setAccountTTL`, `account.sendChangePhoneCode`, `account.changePhone`, подтверждение почты;
- **Чаты:** `channels.editCreator` (передача владения);
- **Платежи:** все `payments.*`, которые тратят или передают: звёзды, подарки, улучшения, перепродажа. Чтение остаётся открытым.

Платежи можно разрешить отдельной настройкой «Разрешить плагинам платежи», по умолчанию она выключена и включается только после предупреждения. Вход, пароль, сеансы и удаление аккаунта для плагинов закрыты всегда.

**Как определяется, что запрос от плагина:**

- на стеке Java есть кадры моста Chaquopy (обратные вызовы, хуки, прокси);
- или поток создан не Java (у его первого кадра нет `run()` потока или главного цикла), то есть это поток Python.

Тогда имя плагина спрашивается у стража по кадрам Python этого потока. Даже если плагин подменил функцию определения имени, запрос всё равно блокируется, без имени. Потоки самого приложения (главный, `DispatchQueue`, пулы) Python не трогают.

**Заблокированный запрос не отправляется.** Его обратный вызов получает ошибку `403 SOLEGRAM_PLUGIN_BLOCKED`, поэтому ничего не зависает в ожидании ответа.

**Хук `pre_request_hook`** не может подменить безобидный запрос запрещённым. Иначе запрос отправился бы уже со стека приложения.

`native_sendRequest` сделан закрытым. Отправить байты в обход проверки теперь можно только рефлексией, а её отмечает анализатор.

### 2.7. Установщик пакетов (`solegram_pip.py`)

**Новое.** Зависимости плагинов (`__requirements__`) ставятся с PyPI так:

- **Папка пакетов стоит последней в пути импорта.** Раньше она была первой. Пакет больше не может подменить модуль Python, SDK или пакеты, которые идут с Solegram.
- **Запрещённые верхние имена.** Пакет не устанавливается, если хотя бы одно его верхнее имя совпадает с одним из:
  - стандартной библиотекой;
  - `java`, `com`, `android`, `org`, `dalvik`, `chaquopy`;
  - `site`, `sitecustomize`, `usercustomize`, `pip`, `setuptools`;
  - модулями SDK и среды;
  - пакетами, которые идут с Solegram;
  - пакетами других плагинов.
- **Запрещённые файлы.** Пакет не устанавливается, если в нём есть нативный код или файлы автозапуска: `.so`, `.pyd`, `.dylib`, `.dll`, `.dex`, `.jar`, `.apk`, `.aar`, `.pth` и подобные. Метка «чистый Python» в имени колеса этого не гарантирует.
- **Проверка кода.** Каждый `.py` пакета проходит тот же анализ, что и плагины. Пакет с вердиктом «опасный» не устанавливается, в ошибке названы файл и причина.
- **Как было и раньше:**
  - контрольная сумма колеса сверяется с индексом;
  - пути с `..` и абсолютные пути отклоняются.

### 2.8. Устойчивость

- **Безопасный режим:**
  - включается сам, если приложение падает при запуске плагинов;
  - запоминает виновника;
  - запускает приложение без плагинов.
- **Хуки защищены от зависаний:**
  - время выполнения хуков отслеживается;
  - ошибки изолированы, ошибка плагина не роняет запрос.

### 2.9. Сервер разработчика

- Работает только в режиме разработчика.
- Слушает только `127.0.0.1`.
- Каждое новое подключение подтверждает человек на телефоне.
- Пока приложение в фоне, подключение отклоняется.
- После «Запретить» новые подключения несколько секунд отклоняются без вопросов.
- То, что ставит разрешённое подключение, считается принятым пользователем.

| A-11 | Плагин мог писать в кэш сгенерированных классов (`plugin_dex`) и в файлы самого Python: внедрение кода, который выполнит среда | Высокая | Исправлено: запись запрещена (2.5) |
| A-12 | Чтение `tgnet.dat`, `shared_prefs`, `cache4.db` через Python (основной способ кражи сессии) | Критическая | Исправлено для Python. Через Java — остаточный риск R-1 |
| A-13 | Сервер разработчика: после разрешённого подключения 2 минуты пускается любое переподключение с `127.0.0.1` | Низкая | Принято: только в режиме разработчика, по явному разрешению |

### Остаточные риски

- **R-1. Целенаправленная атака на сам Solegram.** Через рефлексию Java (`obj.getClass().forName(…)`, `XposedHelpers.findClass`) плагин может получить любой класс, прочитать любой файл приложения через `java.io` и изменить состояние защиты в памяти. Этого не предотвратить в одном процессе.
  - **Чем снижается:**
    - анализатор отмечает рефлексию, доступ к внутренностям плагинов, упоминания файлов сессии и попытки найти защиту;
    - сочетания из этого дают вердикт «опасный», а опасные плагины блокируются по умолчанию;
    - найденные случаи попадают в список блокировки.
- **R-2. Ложные срабатывания стража.** Плагин, который использует, например, сеть только через имена, недоступные анализу, будет остановлен. Это сознательное решение: такое поведение и есть признак маскировки. Авторам честных плагинов достаточно писать вызовы явно (см. П-6).
- **R-3. Полнота анализа.** Статический анализ эвристический. Новые приёмы маскировки добавляются в правила с увеличением `PluginSecurity.VERSION`.

## 4. Протоколы

### П-1. Установка плагина (пользователь)

1. Ставьте плагины только из источников, которым доверяете.
2. Прочитайте отчёт проверки:
   - «Опасный» — не устанавливайте;
   - «Секреты», «Код» и «Система» с высокой или критической отметкой — повод отказаться.
3. Не выключайте «Проверять перед установкой» и «Блокировать опасные плагины».
4. Не включайте «Разрешить плагинам платежи», если не уверены в каждом включённом плагине.
5. Если Solegram сообщил, что остановил плагин, или файл плагина «изменился после проверки», удалите плагин. Не включайте его снова, пока не узнаете, почему так произошло.
6. Если заподозрили кражу:
   - Настройки → Устройства → завершить все другие сеансы;
   - смените облачный пароль;
   - пришлите SHA-256 плагина (страница плагина → Безопасность) по П-3.

### П-2. Реагирование на вредоносный плагин (сопровождающие)

1. **Получить файл.** Посчитать SHA-256 (`sha256sum file.plugin`).
2. **Подтвердить.** Прогнать файл через анализатор и вручную найти вредоносную часть: что крадёт, куда отправляет. Без подтверждения хеш в список не добавляется.
3. **Добавить в `plugins_blocklist.txt`** в репозитории дистрибутива: одна строка `хеш  # название, что делает, дата`. Коммит подписывается как обычно, в сообщении указывается причина.
4. **Сроки.** Подтверждённый стилер сессии или вредоносный плагин, забирающий платежи, добавляется в течение 24 часов с момента подтверждения.
5. **Проверить**, что файл доступен по `raw.githubusercontent.com/SBLauncherRBLX/Solegram/main/plugins_blocklist.txt`. Клиенты подтянут его в течение нескольких часов.
6. **Если приём новый** (анализатор его не отметил), добавить правило в `PluginSecurity`:
   - увеличить `VERSION`;
   - добавить образец в проверочный набор;
   - выпустить версию.
7. **Уведомить пользователей** в канале: название плагина, что он делает, что сделать (П-1, шаг 6).
8. **Удалять хеш из списка** только если плагин признан безопасным по ошибке, и с записью причины.

### П-3. Сообщение об уязвимости

- Об уязвимостях Solegram, включая обход проверок плагинов, сообщайте **приватно** через «Report a vulnerability» (GitHub Security Advisories) в репозитории `SBLauncherRBLX/Solegram`. Не через публичные issues.
- Приложите версию Solegram, шаги воспроизведения и, если есть, файл плагина.
- Мы подтверждаем получение и сообщаем о ходе исправления. Подробности публикуются после выхода исправления.
- Не используйте чужие аккаунты и данные для проверки: только свои тестовые аккаунты.

### П-4. Выпуск версий (сопровождающие)

1. **Ключ подписи:**
   - хранится вне репозитория;
   - защищён паролем;
   - имеет резервную копию у владельца проекта.
   - Сертификат: SHA-256 `0a593fe5…4862ce53`. APK с другим сертификатом не является сборкой Solegram.
2. **Секреты** (ключи API, пароли, код доступа к бетам) хранятся только в `local.properties`, который не попадает в git, и в настройках окружения. Никогда не в коде и не в коммитах. Официальные ключи API Telegram в Solegram не используются.
3. **Каждая сборка** проверяется: подпись APK ключом выше, успешная компиляция.
4. **Беты** публикуются зашифрованными (`beta/*.sealed`: AES-256-CTR, ключ из кода доступа через PBKDF2, HMAC-SHA256). Перед публикацией загруженный файл расшифровывается и сверяется по SHA-256 с собранным APK.
5. **Исходники** каждой версии зеркалятся в `source/` репозитория дистрибутива (GPL-2.0).

### П-5. Изменения движка плагинов (разработчики Solegram)

1. Любое изменение правил анализатора сопровождается увеличением `PluginSecurity.VERSION`.
2. Анализатор написан на чистой Java и проверяется на компьютере на образцах. В них должны быть хотя бы:
   - обычный плагин (ожидается «безопасный»);
   - стилер сессии с отправкой в бот («опасный»);
   - замаскированный `exec` раскодированного кода («опасный»);
   - попытка найти стража («опасный»).
3. Страж (`solegram_guard.py`) проверяется на компьютере с заменой модуля `java`, на Python 3.11. Сценарии:
   - чтение `tgnet.dat` и `shared_prefs`, в том числе через `..`, из потока плагина, через символическую ссылку;
   - запись кода в папку плагинов и `.so` в данные приложения;
   - сеть и `exec` без разрешения и с ним;
   - `dataclass` и стандартная библиотека не должны блокироваться;
   - `gc.get_objects`, `jclass("java.lang.Runtime")`, `from java.lang import Runtime`;
   - определение плагина изнутри вызова Java.
4. Новый способ, которым плагины получают доступ к Java или файлам, должен проходить через проверку стража.
5. Новый запрос Telegram, дающий доступ к аккаунту или деньгам, добавляется в щит аккаунта.
6. Ничто из среды или SDK не должно выполнять код из строк, читать секреты или ходить в сеть от имени плагина без его разрешения.

### П-6. Авторам плагинов

- Пишите вызовы явно: `import requests`, `jclass("java.net.URL")`, `exec(...)`. Тогда они видны в отчёте, пользователь видит, что делает плагин, и страж это разрешает. Имена, собранные из строк, во время работы будут остановлены.
- Плагинам никогда не доступны:
  - файлы сессии, настройки и базы приложения;
  - вход на другие устройства, пароль, сеансы, удаление аккаунта, смена номера;
  - изменение других плагинов, пакетов и среды.
  
  Платежи доступны, только если пользователь сам разрешил.
- Зависимости должны быть чистым Python без нативных файлов, без модулей с именами стандартной библиотеки и без `.pth`.
- Не используйте `gc` для поиска объектов, `sys._current_frames` и внутренности `java.chaquopy`: это признак обхода защиты, такой плагин получит вердикт «опасный».
